# Amy Jaffe Nutrition — contributor guide

## Scope and safety

- This is Amy Jaffe Nutrition's public brochure site. Preserve the existing
  static-site architecture and the current FormSubmit integrations unless a
  change explicitly calls for something different.
- Do not publish, change DNS, alter the Nginx configuration, or send a form
  submission without explicit authorization for that action.
- Keep real inquiries out of test runs. If a production-form test is
  authorized, clearly identify it as a test and use only the approved dummy
  details.

## Local checks

- Use Node 22 or newer and the checked-in `package-lock.json`.
- Run `npm test` before a release. It builds the site, exports the static
  pages to `dist/client`, and runs the rendered-page checks.
- Run `npm run lint` for source changes. Existing image warnings should be
  reported but do not block a release unless they become errors.
- The files that Hetzner serves are in `dist/client`, generated by
  `npm run build:pages`; do not upload source files or `dist/server`.

## Production release

The public production domain is `https://www.amyjaffenutrition.com`.
GitHub's `main` branch triggers the GitHub Pages workflow, and the primary
site is served by Nginx on the Hetzner host at `157.90.162.50`.

Before beginning an authorized release, establish a fresh GitHub baseline with
`git fetch origin main` and confirm that local `main` is not behind
`origin/main`. Preserve any unrelated working-tree changes rather than
discarding or overwriting them.

After the checks pass:

1. Commit the validated source and push `main` to `origin`. Confirm the
   remote branch points at the pushed commit and wait for the GitHub Pages
   workflow to finish successfully.
2. Build the exact commit locally with `npm run build:pages` (or reuse the
   checked build only when the source has not changed). Confirm that
   `dist/client/index.html` exists.
3. On Hetzner, keep `/var/www/amy-jaffe-nutrition` as a symlink to one
   versioned directory under `/var/www/amy-jaffe-nutrition-releases`. Upload
   the new static build to a fresh, inactive release directory first. Never
   copy files directly into the active release.
4. After the upload is complete, atomically repoint the active symlink. A safe
   pattern, once `release` contains the absolute new release path, is:

   ```sh
   ln -s "$release" /var/www/amy-jaffe-nutrition.next
   mv -Tf /var/www/amy-jaffe-nutrition.next /var/www/amy-jaffe-nutrition
   ```

   Name releases with a UTC timestamp and the short Git commit, for example
   `20260814153000-a1b2c3d`, so the previous target remains obvious for a
   rollback.
5. Probe the origin after switching, including the changed page or asset. For
   an origin-specific HTTPS probe, use
   `curl --resolve www.amyjaffenutrition.com:443:157.90.162.50` so a cached
   edge response cannot mask an incomplete upload. Then check the normal
   public URL.

If a production probe fails, restore the previous release by atomically
repointing the same symlink to the previous known-good release, then probe it
again. Do not remove old releases during the deployment; retain them for
rollback until a separately authorized cleanup.
